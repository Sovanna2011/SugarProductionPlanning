Who may do what, answered by the system itself

The planning system now signs people in against its own user table and enforces four roles. Every status code on this page was returned by the running server: ten endpoints were called as each of five accounts and once with no session at all, and the answers recorded verbatim.

A record of a test run, not a live system. The application runs on a private host; this page carries what it answered so the behaviour can be reviewed and passed around without deploying anything. Nothing here talks to a server.

The rules behind those answers

Roles

Roles describe jobs on the site rather than screens in the application, so a new screen inherits an answer to “who may use this” instead of needing a role invented for it.

RoleMay
ADMINEverything, including user administration and forcing a posting that capacity validation blocked
PLANNERMaintain master data and the daily storage plan
WAREHOUSEPost receipts, issues, transfers and reservations
VIEWERRead every screen; every write is refused

Sessions

  • Passwords are bcrypt digests. The password itself is never stored, logged or returned.
  • Sessions are server-side and only the SHA-256 of the token is stored, so a copy of the database yields nothing usable.
  • The cookie is HttpOnly and SameSite=Lax. A bearer token is accepted too, which is how the runs on this page were made.
  • Signing out, changing a password or deactivating an account ends the sessions at once, not at the next expiry.
  • A wrong password, an unknown user and a deactivated account all return the same sentence, so the staff list cannot be read off the login screen.
  • Five wrong passwords hold the account for fifteen minutes — a delay, not a lock.

Running it yourself

No account is created by a migration. A migration runs on every deployment, so seeding accounts there would give every installation the same known passwords and there would be no moment at which somebody decided that was acceptable. 

docker compose up --build
docker compose exec app spp-seed-demo             # the 2026/27 plan's own stock position
docker compose exec app spp-seed-users -demo      # the five accounts on this page

SPP_AUTH_MODE=local SPP_OVERRIDE_ROLE=ADMIN docker compose up -d app
# then open http://localhost:8080

For anything real: spp-seed-users -admin <name> generates a password, prints it once, and requires it to be changed at first sign-in — then spp-seed-users -remove-demo.

The five demo accounts share the password Demo-Sugar-2027, which is in the source, in the documentation and on the login screen. One password across five accounts is exactly what nobody should do with real ones; it is right for these because they exist to be signed in as by whoever has the page open.

That is only acceptable because a database holding them says so: the accounts carry an is_demo flag, the server warns about them on every start, and spp-seed-users -remove-demo deactivates them without deleting the history that names them.
