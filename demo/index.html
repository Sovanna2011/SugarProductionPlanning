The demo system

The whole thing — database, API, dashboard, the 2026/27 season plan, a stock position and five accounts — in one command. Built for putting in front of the people who would use it and watching what happens.

Run it

From nothing to a system you can sign in to.

git clone https://github.com/Sovanna2011/SugarProductionPlanning
cd SugarProductionPlanning
docker compose -f docker-compose.demo.yml up --build

Then open http://localhost:8080.

On a machine with Go and PostgreSQL but no Docker, ./scripts/demo.sh gives the same result. Add --date 2027-04-10 to start from the raw sugar peak instead — 109,720 t against 110,000 t of capacity, which is the more interesting day because the system is nearly full.

Every step is safe to repeat, so restarting neither duplicates the data nor fails.

Sign in as

All five: password Demo-Sugar-2027, also listed on the login screen.

User Roles What changes
admin ADMIN Everything, plus the Users screen and forcing a posting that capacity validation blocked
planner PLANNER Master data and the daily plan. The remelt issue button is off
warehouse WAREHOUSE Receipts, issues and reservations. The master data buttons are off
refinery WAREHOUSE + PLANNER Two roles at once: moves stock and maintains the plan
viewer VIEWER Every screen readable, every write refused
These accounts have a published password. That is what makes them useful and what makes them unsuitable for anything real. They carry an is_demo flag, the server warns about them on every start, and spp-seed-users -remove-demo deactivates them without deleting the history that names them.

What it looks like

Before you start clicking

Give people tasks, not a tour

docs/demo-user-test.md is a script: four to six tasks per role, phrased as work rather than as features. Watch without helping — where somebody hesitates is the finding, and what they reach for first is worth more than their opinion afterwards.

  • Without being told, say which storage is closest to full.
  • Receive enough sugar to push a warehouse past its safe level. Is it clear whether the posting went through?
  • Correct a molasses tank's capacity to whatever it really is.
  • Force a blocked posting with a reason, then find that reason again afterwards.

Four questions the software cannot answer

  • Are the placeholder capacities right? The molasses tanks at 5,000 t each and the conditioning silo at 2,000 t are illustrative figures from the requirement document, marked EXAMPLE in every row. Somebody on site knows the real numbers.
  • Should Finished Sugar Warehouse 2 be active? It is in the storage structure but not in the plan, so it is seeded inactive rather than given an invented capacity.
  • Do the alert bands match how the factory behaves? 95% currently means critical. If people act at 90%, it should say so at 90%.
  • Do four roles match how the site is organised? If the person who maintains the plan also posts stock, that might be a role of its own.

This page is a starting point, not a running system. There is no hosted instance to link to; the command above is what gives you one, on your own machine, with your own database.

Before it holds anything real: remove the demo accounts, create an administrator with spp-seed-users -admin <name>, set SPP_SESSION_COOKIE_SECURE=true behind HTTPS, and change the database password. All of it is in docs/security.md, which is written as an honest account of where the system stands rather than a reassurance.
