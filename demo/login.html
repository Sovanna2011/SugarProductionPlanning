The screens hide what this caller may not do using these answers, rather than working the role table out again in JavaScript — so what the interface offers and what the API accepts cannot drift apart.

The session cookie a real sign-in sets. HttpOnly keeps it away from any script on the page and SameSite=Lax stops another site causing the browser to send it. Only the SHA-256 of that token is stored on the server, so a copy of the database yields nothing usable.

The five accounts share a password published in the project's own documentation. That is what makes them useful here and what makes them unsuitable for anything real: they carry an is_demo flag, the server warns about them on every start, and spp-seed-users -remove-demo deactivates them without deleting the history that names them.

For a real deployment, spp-seed-users -admin <name> generates a password, prints it once, and requires it to be changed at first sign-in.
